# PAMELA patch policy (Phase 4, lab-only)

Auto-patching is **off by default** and exists only as an operator-run executor against a
disposable clone of the managed lab image. The backend API, the dashboard and the LLM have
no path to it. Containment (`block_ip`, `isolate_host`, `reset_password`) is a different
policy (`docs/security/INCIDENT_DECISION_POLICY.md` §5) and still requires a human.

## 1. Eligibility (all checks must pass)

Implemented in `backend/app/pamela_patch.py::check`; the first failing check is the reason.

| # | Requirement | Denial reason |
|---|---|---|
| 1 | Auto-patch armed for this run (`--enable` / `PATCH_AUTO_ENABLE=1`) | `auto_patch_disabled` |
| 2 | Severity not high/critical | `needs_human` |
| 3 | Severity low or medium | `severity_not_eligible` |
| 4 | Severity at or below `PATCH_MAX_SEVERITY` (default medium) | `above_configured_max` |
| 5 | Attack type is `rce` | `unsupported_attack` |
| 6 | Pipeline finished (`done`), not queued/running/failed | `not_decided` |
| 7 | Verification is `verified`, not partial/insufficient | `unverified_evidence` |
| 8 | Template exists in the registry | `unsupported_template` |
| 9 | Template file hash matches its manifest | `template_hash_mismatch` |
| 10 | Target exists and is managed | `unmanaged_target` |
| 11 | Asset criticality is `lab` | `asset_not_eligible` |
| 12 | Running image equals `template.applies_to` | `target_mismatch` |

Checks 1–7 are incident policy; 8–12 are supply-chain/target identity.

## 2. Registry

`lab/patch/templates/<id>/manifest.json` + the replacement file. Only one template exists:

| Template | Version | SHA-256 | Applies to | Change |
|---|---|---|---|---|
| `v1_sanitize_ping` | 1 | `a4143b8c…2f5f1` | `pangbela-lab-app` | Removes `/bin/sh -c` from `/vuln/ping`. Unsigned injection is refused before exec; the signed maintenance operation runs a fixed `printf` argv. |

Adding a template means a new versioned directory and a reviewed manifest; the executor
refuses any file whose hash differs.

## 3. Workflow

```
policy check → dry run (diff, no writes) → clone from the target's exact image
→ snapshot /lab/app.py + hash → apply template → restart clone
→ health 200 → exploit 400 without marker → safe endpoint 200
→ success: audit "applied"  |  any failure: restore snapshot, restart,
  prove the exploit works again, audit "rolled_back"
```

The canonical lab service is never modified, so T1/T2/T4 remain reproducible afterwards.
Rollback evidence is the exploit returning `200 LAB_RCE_OK` after restore.

## 4. Commands

```sh
# deny by default
python3 lab/patch/apply.py --incident-file lab/patch/fixtures/eligible_medium.json

# dry run (no writes)
python3 lab/patch/apply.py --incident-file lab/patch/fixtures/eligible_medium.json --enable --dry-run

# apply + verify
python3 lab/patch/apply.py --incident-file lab/patch/fixtures/eligible_medium.json --enable

# failure injection: apply, fail verification, roll back
python3 lab/patch/apply.py --incident-file lab/patch/fixtures/eligible_medium.json --enable --force-failure

# a real incident (denied until the LLM pipeline produces a done/verified verdict)
python3 lab/patch/apply.py --incident <uuid> --enable
```

Audit files: `lab/patch/audit/<utc>-<incident>.json` (policy decision, template hash,
image id, before/after hashes, checks, result, rollback check).

## 5. Safety boundaries

- Operator tool only; no HTTP endpoint, no LLM tool, no shell generated by a model.
- Clone: `--network none`, `--cap-drop ALL`, `no-new-privileges`, 256 MB limit.
- Patch content is a reviewed file, not model output; hash checked before use.
- Target identity checked against the running container's image and the manifest.
- Audit trail is append-only files on the host; every run writes one, including denials.

**Ceiling.** This demonstrates the mechanics on a disposable clone, not a production
deployment: there is no staged rollout, no dependency patch type, no database-backed patch
status, no dashboard view, and no post-patch monitoring window. The approved-operation
(maintenance) path is not re-exercised on the clone. Before production: pinned image
digests, a patch worker with scoped credentials, staging service, health/rollback policy,
and DB-backed audit.

**Known gap.** A real incident cannot become eligible while GATER is unavailable: the
policy requires a finished pipeline with a verified verdict. The allowed-path demo
therefore uses `lab/patch/fixtures/eligible_medium.json`, explicitly a policy fixture.
Running the executor against the real T2 incident returns `not_decided`, which is the
honest result and is kept as audit evidence.

## 6. Phase 4 acceptance matrix

| Test | Result |
|---|---|
| Low eligible patch | PASS (unit) |
| Medium eligible patch | PASS (unit + real clone patch) |
| High/Critical automatic patch denied | PASS (unit + CLI) |
| Unsupported template denied | PASS (unit) |
| Unknown/partial evidence denied | PASS (unit) |
| Unmanaged target denied | PASS (unit) |
